# Stewardship hosted files

This specification defines a small library of files for parishioners that the
deployment hosts (issue #346): PDF and Office documents that Families download,
and images shown inline in Family pages and emails. Page and email content
refers to a file with a `{{ file.<slug> }}` placeholder that expands to the
file's public link. The first use is a PDF linked from Member update content.

The library reuses the campaign artwork pipeline's storage, re-encoding and
serving patterns (`accounts/branding_files.py`, `web/content.py`,
`accounts/branding_views.py`) rather than inventing new ones. Content rules
that it extends are defined in
[content and email templates](../data/spec.md#content-and-email-templates);
the Admin page follows the shared [Admin tables](../admin-portal/spec.md#admin-tables)
and [page help](../admin-portal/spec.md#page-help) conventions.

## Scope and decisions

- **One library per deployment**, shared by every campaign. It is not tied to
  a campaign or to a configuration version.
- **Administrators only** may view the library, upload, rename and delete.
- **Upload or delete, never edit.** A file's bytes never change after upload.
  Replacing a document means uploading a new file, pointing content at it and
  deleting the old one.
- **Unguessable public links.** Each file has a random 256-bit token. Anyone
  with the link can open the file without signing in, so links work in emails.
  Files are never listed or discoverable publicly.
- **Placeholders** `{{ file.<slug> }}` work in every page and email body and
  expand to the file's absolute HTTPS link.
- **Library limits:** 10 MB per file, at most 100 files and 200 MB in total.

## File record and storage

A new table, `stewardship_hosted_file`, holds one row per file. It is a mutable
record (created/updated timestamps, version, actor and correlation IDs, as the
[storage principles](../data/spec.md#storage-principles) require) whose only
changeable field is `slug`; a database trigger refuses any other change, as
the branding bundle trigger does.

| Column | Rule |
| --- | --- |
| `id` | Opaque UUID primary key, generated by the server. |
| `slug` | Unique. 1–64 characters matching `^[a-z0-9]+(-[a-z0-9]+)*$`: lowercase ASCII letters, digits and single hyphens, with no leading or trailing hyphen. |
| `original_name` | The uploaded file's base name after cleaning (below), 1–200 characters. Shown to Admins and used for the download name. |
| `kind` | The type detected from the content: `pdf`, `docx`, `xlsx`, `pptx`, `png` or `jpeg`. The Content-Type is derived from it and is never stored or taken from the browser. |
| `size` | Stored byte count, 1 to 10,485,760 (10 MB). |
| `sha256` | Lowercase hex digest of the stored bytes. |
| `width`, `height` | Pixel size of an image, 1–2,048; null for documents. Both are set exactly when `kind` is `png` or `jpeg`. |
| `token` | Unique. 43 characters of URL-safe base64 (`^[A-Za-z0-9_-]{43}$`) from 32 bytes of `secrets.token_urlsafe`. |
| `uploaded_by_id` | The uploading portal user; immutable. The upload time is `created_at`. |

The detected `kind` values name what is stored, so an uploaded GIF is recorded
as `png` after re-encoding (see [accepted types](#accepted-types-and-validation)).

Cleaning the original name: take the final path component (after both `/` and
`\`), normalize to Unicode NFC, remove control characters and the characters
`"*/:<>?\|`, collapse runs of white space, trim, and cut to 200 characters. If
nothing is left, use `file`. The stored name keeps its extension as uploaded;
the served download name replaces it with the detected type's extension.

**Bytes live on disk, not in the database**, as campaign artwork does. Each
file is one regular file at `<media>/hosted-files/<id hex>` (owner-only
`0600`, directory `0700`, no extension and no user-supplied path component),
under the deployment's durable media root from
[runtime storage](../operations/spec.md#runtime-storage). The path is derived
from `id` and is not stored. Reads open the file with `O_NOFOLLOW` and check
that it is a regular, single-link, owner-only file whose size matches the row,
as `read_variant` does for artwork.

Upload and deletion hold an exclusive storage lock (`hosted-files/.lock`, the
same non-blocking `flock` pattern as the branding `media_lock`) from before the
disk write until the database transaction ends:

1. Upload validates and normalizes the bytes in memory, writes them with
   `O_CREAT|O_EXCL`, calls `fsync` on the file and the directory, and only then
   inserts the row. A failure after the write removes the file.
2. Deletion deletes the row (the database refuses a deletion that is still in
   use, see [deletion](#deletion)), commits, and then unlinks the file.
3. While holding the lock, each upload and deletion also removes any file in
   `hosted-files/` that has no row, which can be left by a crash between a disk
   step and its commit. The sweep never follows links and removes only names
   that are 32-character hex UUIDs.

Serving starts from the row, so a leftover file is never served, and a row
whose file is missing serves the [unavailable page](#unknown-and-deleted-files).

The library caps are enforced by the database: an insert trigger takes a
`SHARE ROW EXCLUSIVE` lock on the table and refuses the row when the library
would exceed 100 files or 200 MB in total, so two concurrent uploads cannot
both pass.

The table, its triggers and the [reference view](#current-content) are
part of the fresh-install schema baseline, which landed before the
[v1 schema freeze](../../../plans/stewardship/v1-launch.md#production-readiness-activation-and-schema-freeze).
Any later change to them follows the
[post-launch schema policy](../operations/spec.md#post-launch-schema-policy).

Hosted files are not part of the YAML configuration. They are uploaded data,
like artwork bytes, and a configuration round-trip would add versioning the
library deliberately does not have. Content in the YAML configuration refers
to them by slug.

## Accepted types and validation

The type is detected only from the file's content, never from its name, its
extension or the browser's declared type. A file that matches none of the
accepted types is refused. Uploads larger than 10 MB (10,485,760 bytes) are
refused before any parsing.

| Detected type | Accepted when | Stored as |
| --- | --- | --- |
| PDF | Starts with `%PDF-` at byte 0 and has `%%EOF` within its last 1,024 bytes. | As uploaded. |
| Word (`.docx`) | A valid OOXML package (below) whose main part is `application/vnd.openxmlformats-officedocument.wordprocessingml.document.main+xml`. | As uploaded. |
| Excel (`.xlsx`) | Main part `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet.main+xml`. | As uploaded. |
| PowerPoint (`.pptx`) | Main part `application/vnd.openxmlformats-officedocument.presentationml.presentation.main+xml`. | As uploaded. |
| PNG | Decodes as a single-frame PNG. | Re-encoded PNG. |
| JPEG | Decodes as a JPEG, including a multi-picture (MPO) JPEG from a phone or camera, whose first picture is kept. | Re-encoded JPEG. |
| GIF | Decodes as a GIF with exactly one frame. | Re-encoded PNG. |

**OOXML packages** are checked with the standard `zipfile` module, without
extracting any part except `[Content_Types].xml` and the small relationship
(`*.rels`) parts, each read only up to 1 MB and all of them up to 8 MB:

- the archive opens, has at most 10,000 entries, no entry name is absolute
  or contains a `..` component, and no two entry names are equal ignoring
  case (a repeat would let the checked copy differ from the one a reader
  uses);
- `[Content_Types].xml` exists, is at most 1 MB uncompressed, contains no
  `<!DOCTYPE`, and parses as XML;
- exactly one of the three accepted main content types above is declared; and
- the package has none of these kinds of active content: no part named
  `vbaProject.bin` or `vbaData.xml`, no part under an `activeX/` folder, no
  content type containing `macroEnabled`, `vba`, `macrosheet` (Excel 4.0
  macro sheets), `activeX` or `dialogsheet`, no embedded OLE object or
  macro-enabled package under an `embeddings/` folder (`.bin`, `.docm`,
  `.xlsm`, `.pptm`, `.dotm`, `.xltm`, `.potm`), and no relationship,
  internal or external, of type `attachedTemplate` (a remote template can
  deliver macros to a clean `.docx`), `oleObject`, `subDocument`, `frame`,
  `control` or `activeXControlBinary` (ActiveX), `aFChunk` (an imported
  RTF or HTML chunk, which can carry OLE objects), `vbaProject` or ribbon
  `extensibility` (`customUI`). Office finds parts by relationship and
  content type, not by folder, so these catch parts moved elsewhere too.
  Relationship types are compared after trimming white space and ignoring
  case.

**Embedded OLE objects are refused** (Admin decision, 2026-09-29 review), even
though some legitimate documents contain them, because this is the safer
default for files the parish publishes on its own domain. An Admin whose file
is refused saves a copy without embedded objects, or as a PDF. Ordinary
hyperlinks and embedded charts (stored as `.xlsx` packages) are accepted.

Macro-enabled formats (`.docm`, `.xlsm`, `.pptm`), templates (`.dotx`,
`.xltx`, `.potx`) and slide shows (`.ppsx`) therefore fail the main-type or
macro check and are refused.

**Older Office formats (`.doc`, `.xls`, `.ppt`) are refused.** They are OLE2
compound files (signature `D0 CF 11 E0 A1 B1 1A E1`), which carry VBA macros in
ways that cannot be ruled out without a full OLE parser. Office has saved OOXML
by default since 2007, so an Admin can re-save the file. Password-protected
OOXML files are also OLE2 containers and are refused by the same check. The
refusal message covers both cases.

**Images** follow the artwork normalizer (`_normalized_variants` in
`web/content.py`), with limits sized for this library:

- The file is opened with Pillow restricted to PNG, JPEG and GIF, with
  decompression-bomb warnings treated as errors. Up to 16,000,000 pixels are
  accepted (`MAX_IMAGE_PIXELS`), and the image must pass `verify()`.
- **Animated GIFs are refused.** Animation adds decoder surface, displays
  inconsistently across email clients, and needs a pause control under WCAG
  2.2.2. The same "one frame" rule already applies to artwork. SVG, WebP, HEIC
  and every other image type are refused.
- EXIF orientation is applied. The image is then fitted within 2,048 pixels
  per side and copied into a fresh pixel buffer, which discards EXIF, ICC, XMP
  and text chunks.
- PNG and GIF input is saved as PNG (RGBA, keeping transparency). JPEG input is
  converted to RGB and saved as JPEG at quality 85, because photos saved as PNG
  would be several times larger.
- The re-encoded output must also be at most 10 MB. The stored `size`,
  `sha256`, `width` and `height` describe the output.

**PDF and Office files are stored byte-for-byte.** No content scan, macro
stripping or antivirus step is done. Those formats need parsers that the
deployment does not otherwise carry, and the controls that matter are:
only Administrators upload, macro-carrying Office formats are refused, and
documents are always served as downloads under a sandbox policy (see
[public serving](#public-serving)). PDFs may contain JavaScript or launch
actions. Those run only in a reader after download, never in the site's
origin (the response is an `attachment`, `nosniff` and sandboxed), and PDF
readers restrict them. That client-side risk is accepted and is the same as
for any PDF an Administrator could email directly.

These kinds of Office content are **accepted as residual risk**, since only
Administrators upload, downloads are `attachment`s, and each needs the
reader's own Office to act on it: DDE fields and formulas (which Office now
disables by default), external or UNC images (which can reveal a Windows
sign-in hash to another server when the document is opened), Excel external
workbook links, and a macro-enabled workbook embedded under a plain `.xlsx`
name through a `package` relationship (it runs only if the reader opens the
embedded object, and Office's own macro prompt still applies).

## Public serving

Each file is served at `/files/<token>`. The `{{ file.<slug> }}` placeholder
expands to the absolute link `<public origin>/files/<token>`, using the
deployment's configured public origin (the same origin the campaign banner
uses). The link uses the token, not the slug. So a
[slug rename](#slug-changes) never changes a link, and a link reveals nothing
about the library.

The route answers `GET` and `HEAD` only, with no authentication, and ignores
any query string (so mail-client link rewriting still works). It sits outside
the Family and Admin route gates, so it is reachable while the
[Family portal is closed for maintenance](../admin-portal/spec.md#family-portal-maintenance)
and while restore review is pending. A hosted file is parish-published
material, not Family data, and an email already sent should still work. During
an upgrade, Caddy's maintenance page answers as it does for every route.

Every successful response carries:

| Header | Value |
| --- | --- |
| `Content-Type` | Derived from `kind`: `application/pdf`, the three OOXML types, `image/png` or `image/jpeg`. |
| `Content-Disposition` | Documents: `attachment`. Images: `inline`. Both with `filename="<ASCII name>"; filename*=UTF-8''<percent-encoded name>`. |
| `Content-Length` | The stored `size`. |
| `X-Content-Type-Options` | `nosniff` |
| `Content-Security-Policy` | `default-src 'none'; sandbox; frame-ancestors 'none'` |
| `Referrer-Policy` | `no-referrer` |
| `Cache-Control` | `no-cache` |
| `ETag` | `"<sha256>"`; a matching `If-None-Match` gets `304 Not Modified`. |

The download name is the cleaned `original_name` with its extension replaced
by the detected type's (`.pdf`, `.docx`, `.xlsx`, `.pptx`, `.png`, `.jpg`). The
ASCII fallback replaces each non-ASCII character with `_`. The shared security
middleware sets the page CSP and `Cache-Control: no-store` on every response;
a served file marks itself so the middleware applies the sandbox policy above
and keeps its own caching, and every `/files/` response gets `no-referrer`, as
`/access/` responses already do.

`no-cache` with an ETag lets browsers and mail-image proxies keep a copy but
revalidate it cheaply, so a deleted file stops being served on the next
request instead of staying cached for a long `max-age`. No
`Cross-Origin-Resource-Policy` header is sent, because webmail pages load
email images from another origin. Range requests are not supported.

Responses are streamed from the open file after the row lookup, and no
database transaction is held while the file streams. Caddy buffers each
`/files/` response body (up to 11 MB, `response_buffers`) so a slow phone
download never holds a web thread. The resulting memory use (concurrent
downloads × file size) is acceptable at parish scale. A slow-client test
should show that a web thread is released before the client finishes reading.
It is deferred, since it needs the Caddy container
([#346 comment](https://github.com/epiphany40223/parishkit/issues/346#issuecomment-5901731922)); the adapted Caddy
configuration is checked with the pinned image instead, and a manual
rate-limited download on the validation VM is recommended before a
campaign-wide email links a large file.

Hosted-file links are per file, not per recipient, so an inline image cannot
act as a per-Family tracking pixel. Caddy's access log already drops request
paths. No download counts are kept.

### Unknown and deleted files

An unknown token, a deleted file, or a row whose file is missing or fails its
size check returns the same self-contained page: HTTP 404, marked as a safe
application error so the middleware keeps it, with `Cache-Control: no-store`
and `Referrer-Policy: no-referrer`. It says "This file is no longer
available", suggests contacting the parish, and names the parish and links its
website when the deployment is configured. It uses the application stylesheet
only, with no scripts. An `<img>` whose file is gone simply shows its `alt`
text. The page gives no hint about whether a token ever existed, and there is
no tombstone table.

## Placeholders

A file placeholder is `{{ file.<slug> }}`, matched by
`\{\{ *file\.([a-z0-9]+(?:-[a-z0-9]+)*) *\}\}`. Only spaces may appear inside
the braces, never line breaks, so the stored text and the
[reference search](#current-content) match exactly. It is a second
placeholder family beside the existing named placeholders (`PLACEHOLDER` in
`web/content.py`), which keep their syntax and meaning:

- `validate_template` accepts file placeholders in page and email **bodies**
  (HTML and plain text) of every kind: Family pages, invitations, reminders,
  confirmations and their closing note, and Family tests. Any other
  leftover `{{`, `}}`, `{%`, `%}`, `{#` or `#}` is still refused.
- File placeholders are refused in email subjects and share-option labels,
  where a link has no use, and in the daily and weekly Admin digest
  templates (with inline images), since the library is for parishioners.
- `render_template` expands them in the same pass as named placeholders. It
  resolves each slug to the absolute link from one library lookup per render
  and escapes the result like any other substitution. A slug with no file at
  render time expands to `<public origin>/files/unavailable`, which serves the
  [unavailable page](#unknown-and-deleted-files). That can happen only through
  a restore or an archived campaign that is reopened after its file was
  deleted (see [current content](#current-content)). An `<img>` pointing
  there is then removed by the output sanitizer.
- Generated plain text writes a link as `label: {{ file.<slug> }}`, so the
  expanded plain-text alternative carries the full link, as it does for
  `{{ family_url }}`.

The sanitizer (`sanitize_html`) keeps `href="{{ file.<slug> }}"` on `<a>` as it
keeps `href="{{ family_url }}"` today. For link text, Admins write their own,
for example `<a href="{{ file.ministry-guide }}">Ministry guide (PDF)</a>`.

**Unknown slugs are refused at save.** When content is authored or changed
(the content editor, campaign creation from defaults or a clone, and
configuration validation of a new or changed revision), every file placeholder
must name an existing file. The editor names each unknown placeholder and its
part (HTML or plain text), for example "`{{ file.guide }}` does not match any
hosted file". A clone whose source content names a deleted file is refused the
same way; the Admin can upload a file with that slug, since slugs are free for
reuse after deletion. Revisions carried unchanged into a new configuration are
not re-validated, following the existing
[content text rules](../data/spec.md#content-and-email-templates).

To close the race with deletion, creating a configuration request takes
`FOR KEY SHARE` locks on the rows of every slug its patch names, and refuses
the request if a row is missing. Deletion and slug changes take a row lock
that conflicts, so the two serialize: once the request commits, it is a
[pending change](#current-content) that holds the file until it is applied,
and the applied content holds it after that.

Before initial setup completes there is no library. Any file placeholder in
setup-wizard content is therefore unknown and refused.

### Inline images

An `<img>` is allowed in page and email content only when its source is a
hosted image. The sanitizer's allowlist gains `img` with exactly these
attributes:

- `src`, which is required. When no public origin is given, the only accepted
  value is a file placeholder. When one is given, the only accepted value is
  exactly `<origin>/files/<43-character token>`.
- `alt`, which is required and may be empty for a decorative image. It may be
  at most 250 characters.
- `width`, which is optional and must be an integer from 1 to 2,048.

Any other attribute (`height`, `style`, `srcset`, `loading`, handlers) is
dropped. An `<img>` whose `src` is not an accepted value is removed entirely.
`removed_markup` reports it as "image not from the hosted file library".

`sanitize_html` and `prepare_content` gain an optional `origin` argument.
Authoring calls omit it, so stored content keeps only the placeholder form and
a literal image link typed by an Admin, even to this deployment, is removed.
`render_template` passes the deployment origin, so expanded image links
survive the output-boundary sanitize. The delivery checks
(`FamilyDelivery`, `ReadinessMail` and any other check that compares mail
HTML with `prepare_content`) pass the same origin they already use for the
campaign banner. So a hosted image in outgoing mail is accepted only from this
deployment's public HTTPS origin, the same pattern as `without_email_banner`.
The campaign banner keeps its own separate rule.

The content editor also refuses, at save:

- an `<img>` whose placeholder names a document rather than an image ("link
  to it with `<a href>` instead"); and
- an `<img>` with no `alt` attribute ("describe the image, or use `alt=""` if
  it is decorative").

Generated plain text omits images. An image that carries information needs a
text equivalent in the content.

For email clients, the [shared email layout](../data/spec.md#content-and-email-templates)
adds `style="max-width:100%;height:auto;border:0"` to each `<img>` when the
message is built. Its style block gets the matching `.pk-body img` rule. This
happens after the delivery checks, like the layout's link styles. The `width`
attribute is what Outlook for Windows honors. The Admin page's copy action
therefore fills it with the image's width, capped at 600 (the email column).
Many clients block remote images until the reader allows them, so the About
panel tells Admins to keep essential information in text and always write
`alt` text. Family pages show images at most the width of the content column,
through the portal stylesheet.

## Slug changes

An Admin may change a file's slug only while no
[current content](#current-content) references it. The refusal lists where it
is used, exactly as a deletion refusal does. The link (token) never changes.

References are not rewritten. Rewriting would mean silently editing content
across campaigns and configuration versions, including pending requests.
Refusing is simpler and safe, and an unused file can still be renamed freely,
which covers fixing a typo right after upload. To rename a file in use, the
Admin edits the content to use a new slug on a newly uploaded copy, or removes
the references first.

The database enforces the rule too: the update trigger refuses a slug change
while the reference view reports a use.

## Deletion

Deletion removes the row and the file for real. Every link to the file,
including links in emails already sent, then shows the
[unavailable page](#unknown-and-deleted-files). Deletion is refused while
any current content references the slug, both on the Admin page and by a
`BEFORE DELETE` trigger that reads the same reference view. So no code
path can delete a file still in use.

### Current content

A file is **in use** when its slug appears in a file placeholder, or its link
path `/files/<token>` appears, in any of:

1. **Campaign content in the active configuration**: every page and email
   content revision (HTML, plain text and subject) that the active applied
   configuration version holds for a campaign in `draft`, `scheduled`,
   `active` or `closed`, or for an `archived` campaign that is still the
   global current-campaign pointer (it can still be returned to `closed` and
   reopened). This includes every email template, not only those a schedule
   selects, and the Testing-mode draft campaign's content, because Testing
   content lives in the same active configuration.
2. **Pending configuration changes**: the patch of every configuration change
   request whose latest checkpoint is not `applied`, `failed` or `cancelled`,
   the same pending rule as `stewardship_branding_pending_v1`.
3. **Unsent email**: the rendered HTML or plain text of every queued message
   that is not yet in a terminal state. For the Family outbox that means
   `pending`, `submitting`, `retry_wait` or `delivery_unknown`, including
   messages held by a delivery pause. It also covers campaign email tests and
   digest messages still waiting to send. Scheduled emails that are not
   rendered yet are covered by item 1, because their template revisions live
   in the active configuration.

Content of campaigns that are archived and no longer the current pointer,
purged campaigns and historical configuration versions is not current. Such
content can never render again unless an archived campaign is cloned, and a
clone's content is [validated at save](#placeholders).

One SQL view, `stewardship_hosted_file_use`, returns each use as a row: the
file ID, the source (`content`, `pending_change` or `unsent_mail`), the
campaign ID, the content kind and slot where applicable, and a count for
unsent mail. The Admin page, the rename and deletion refusals, and the
guard trigger all read it, so they cannot disagree. The web role reads the
view, not the content, requests and mail it summarizes.

### Refusal and multi-select results

A refusal names each use in plain words, for example "2027 Stewardship ›
Member update introduction (page)", "2027 Stewardship › Initial invitation
(email)", "A change that is still being applied" or "3 emails waiting to be
sent".

Admins delete one file from its row, or several ticked files together,
through the portal's shared
[row actions and confirmation](../admin-portal/spec.md#row-actions-and-confirmation)
dialog ([#879](https://github.com/epiphany40223/parishkit/issues/879)); there
is no separate confirmation or results page. Only unused files offer Delete
and a selection box. Confirming posts the chosen files, and the server
refuses the whole request, deleting nothing, when any of them is in use by
then ("A chosen file is now used by a page, an email or unsent mail, so
nothing was deleted."). Otherwise each file is deleted in its own
transaction, which locks it and rechecks its uses; a file already deleted
counts as deleted. On success the table redraws in place without the files.
Should one fail after others were deleted (it came into use meanwhile, or the
storage lock was busy), the dialog says some were deleted but not all and
asks the Admin to reload; if the first fails, it says nothing was deleted.
This replaced the earlier per-file results page (where one file's refusal
never blocked the others), so the library follows the portal-wide rule that a
request is refused whole when any chosen row cannot be acted on.

## Admin page

**Hosted files** is a page in the Admin menu's **Parish data** group, after
Ministries, at `/admin/parish/files/` (formerly `/admin/files/`, which is
404 since [#864](https://github.com/epiphany40223/parishkit/issues/864)). It
is registered in the
[navigation registry](../admin-portal/spec.md#admin-navigation), with its
form-action routes classified as non-pages. Page text uses plain words: the
slug is labelled **Placeholder name**.

The page leads with a one-line notice ("Anyone with a file's link can open it,
so never upload anything private."); its introduction ("Files you can link
from Family pages and emails.") opens the About panel, following the Admin
[page help](../admin-portal/spec.md#page-help) rules. Then:

- **Upload form**: a file field (`accept` lists the permitted extensions, as a
  hint only) and a **Placeholder name** field with the hint "Lowercase
  letters, digits and hyphens. Leave blank to use the file name." A small
  script fills the field from the chosen file's base name; when it is left
  blank, the server derives it. Deriving means taking the base name without
  its extension, folding it to ASCII, lowercasing it, turning each run of
  other characters into one hyphen, trimming hyphens, and cutting to 64
  characters at a hyphen where possible. An empty result becomes `file`, and a
  taken name gets `-2`, `-3` and so on. A name the Admin typed is never
  changed, only validated; a taken or invalid one is a field error. On success
  the page redirects back with "Uploaded *name* as `{{ file.slug }}`".
- **Usage line**: "12 of 100 files, 35.2 MB of 200 MB used."
- **File table**, built on the shared Admin table component with its
  selection column and **Delete selected** bulk action, as an action table
  ([row actions and confirmation](../admin-portal/spec.md#row-actions-and-confirmation)).
  Its headings sort
  the whole library on the server (Name, Placeholder, Type, Size, Uploaded,
  and Used in by its number of uses), by placeholder name until a heading is
  chosen. The columns are:
  - Preview: a 48-pixel thumbnail for images, loaded from the file's public
    link; a type label for documents.
  - Name: the original file name, which opens the file in a new tab.
  - Placeholder: `{{ file.slug }}` in a read-only field with a **Copy**
    button. Images also get **Copy image tag**, which copies
    `<img src="{{ file.slug }}" alt="" width="N">` with N as the image width
    capped at 600.
  - Type: for example "PDF", "Word document" or "PNG image, 1,200 × 800".
  - Size.
  - Uploaded: the Admin's name and the date, in the parish date format.
  - Used in: the uses from [current content](#current-content), or "Not
    used".
  - Actions, last: for an unused file, **Edit** (its **Change placeholder
    name** page) and **Delete**, icon buttons named for the file ("Edit
    ministry-guide", "Delete ministry-guide"). A file in use has no actions
    and no selection box; its Used in column says where it is used.
- **Empty state**: "No files yet. Upload a PDF, Office document or image to
  link it from pages and emails."
- **About this page** panel: how to write a link and an inline image, with
  examples; accepted types and limits; what Edit, Delete and Delete selected
  do, and that nothing is deleted when a chosen file is in use; why links
  stay the same after a rename;
  that deleting a file breaks links in emails already sent; alt text and
  email-image advice; and how to replace a file.

Copy buttons use the clipboard API (the Admin portal [requires
JavaScript](../admin-portal/spec.md#javascript-requirement)); the read-only
field can also be selected and copied by hand. The Pages and emails editor's
placeholder reference mentions `{{ file.<slug> }}` and links to this page.

## Permissions, audit and limits

- Only Administrators may open the page and use its actions. Staff and
  Ministry leaders get the ordinary denial. The public `/files/<token>` route
  is the only unauthenticated surface.
- Database reads follow who renders content. The web login reads the library
  and the use view (the Admin page, Family pages and previews). The general
  worker (Family mail preparation and chosen-Family tests) and mail dispatch
  (Family mail and receipts re-rendered at send) read only each file's `slug`
  and `token`, which is all that expanding a placeholder needs. The scheduler
  and every other login read nothing. A test renders a file link and an inline
  hosted image under each of these real logins.
- Every action is a CSRF-protected POST. Fresh Google authentication is not
  required, matching content and artwork edits, which also do not require it.
- Audit events (new `Action` values in `audit/schemas.py`, with the `ACTION`
  context gaining closed fields `file_slug`, `previous_file_slug`,
  `file_kind`, `file_size` and `file_fingerprint`, mirrored in
  `stewardship_safe_context_v1`): `hosted_file_uploaded`,
  `hosted_file_slug_changed` (with the before and after slugs) and
  `hosted_file_deleted`. The subject is the file ID. Refused
  actions are not audited. The original file name is not audited, because it
  is free text. A slug is limited to a restricted charset and length, so it is
  safe operational metadata.
- The limits are 10 MB per file, 100 files and 200 MB in total, enforced in
  the application and by the database insert trigger.

## Operations

- **Ingress**: only `POST /admin/parish/files/uploads/` admits a request body
  of up to 11 MB (a 10 MB file plus form overhead); its old address
  `/admin/files/upload` is not kept (#864). Every other route keeps the 6 MB
  `request_body` limit in [production ingress](../operations/spec.md#production-ingress-and-tls).
  The view refuses a `Content-Length` over 11 MB before reading the body.
  Django's file-upload settings keep spooling files over 5 MB to the web
  container's `/tmp` tmpfs. The proxy's 30-second body-read timeout is
  unchanged. A 10 MB upload therefore needs roughly 3 Mbit/s of upload speed,
  which the About panel mentions. Caddy buffers `/files/` responses as
  described under [public serving](#public-serving).
- **Backup and restore**: hosted files live in the media tree, which the
  [backup](../operations/spec.md#backup) file set (`ARCHIVED_TREES` in
  `backup.py`) already archives next to the database dump. The backup's
  archived-tree bound (`MAX_FILES_BYTES`) rises from 256 MB to 512 MB, so a
  full library plus branding fits with room to spare. The dump and the tar are
  taken moments apart. After a restore, a file without a row is removed by the
  next upload or deletion sweep, and a row without a file serves the
  unavailable page and shows as **Missing** on the Admin page, where it can be
  deleted.
- **Housekeeping**: there is no staging area and no scheduled cleanup job.
  The orphan sweep under the storage lock is the only cleanup.

## Security considerations

- The type comes from content signatures and structure, never from names or
  the declared MIME type. No HTML, SVG, XML, script or unknown type is ever
  stored or served.
- Documents are always served as `attachment`, so browsers never render
  uploaded document bytes in the site's origin. Every response is `nosniff`
  and sandboxed with `default-src 'none'`.
- Images are fully decoded and re-encoded from a fresh pixel buffer. No
  metadata survives, and decoding is bounded by the pixel limit.
- Macro-, ActiveX- and OLE-bearing Office packages, remote templates,
  imported chunks and all OLE2 files are refused. Scripts in PDFs and the
  Office residual risks listed under
  [accepted types](#accepted-types-and-validation) are accepted client-side
  risks under Administrator-only upload and attachment serving.
- Storage names are server UUIDs under the private media root, outside any
  web root. Reads refuse links and mismatched files.
- Tokens are 256-bit and random, per file and never per recipient. Links are
  public by design, so no secret or personal document belongs in the library;
  the About panel says so.
- Content can embed images only from this library through placeholders.
  Literal or third-party image links are removed, so parish content cannot
  carry remote tracking content.

## Non-goals

- General file storage, folders, per-campaign libraries, or files for Staff or
  Ministry leaders.
- Editing, versioning or replacing a file in place, or keeping a link while
  its bytes change.
- Private or signed-in-only files, expiring links, download counts or
  analytics.
- Antivirus scanning, PDF sanitizing or Office content conversion.
- Rewriting content references on a slug change.
- An "insert file" picker in the content editor (Admins copy the placeholder
  from the Hosted files page).
- Hosting files that content does not reference. Admins may share a link
  elsewhere, but only content references are tracked.

## Acceptance tests

Unit and database tests must cover:

1. Detection accepts real PDF, DOCX, XLSX, PPTX, PNG, JPEG and single-frame GIF
   samples. It refuses DOCM, XLSM, PPTM, DOTX and PPSX; OLE2 `.doc`, `.xls`
   and `.ppt` files; password-protected OOXML; OOXML with `vbaProject.bin` or
   an `activeX/` part; a ZIP that is not OOXML; a `[Content_Types].xml` with a
   DTD; animated GIF, SVG, WebP, HTML, and a PDF-named text file. It also
   refuses a file whose name or declared type claims an accepted type its
   bytes do not have.
2. Size limits: exactly 10,485,760 bytes is accepted and one more byte is
   refused. An image over 16,000,000 pixels is refused. A JPEG with EXIF GPS
   and an ICC profile is stored without either, oriented, and fitted within
   2,048 pixels. GIF is stored as PNG.
3. Slug validation, the derivation from assorted file names (non-ASCII,
   spaces, empty, taken), and uniqueness under concurrent uploads.
4. The database caps refuse the 101st file and an upload past 200 MB, even
   when two uploads race.
5. Serving: the headers for a document and an image, the ASCII and UTF-8
   download names, `HEAD`, a `304` from `If-None-Match`, an ignored query
   string, and that the sandbox CSP and `no-referrer` survive the security
   middleware. An unknown token, a deleted file and a missing or truncated
   file all return the same 404 page. The route is reachable while the Family
   portal is closed for maintenance.
6. Placeholders: expansion to the absolute token link in HTML and plain text
   for pages and every email kind; refusal in subjects and share labels;
   refusal of unknown slugs at save and at configuration validation, naming
   the placeholder; refusal of line breaks inside a file placeholder; named
   placeholders unchanged.
7. Inline images: the sanitizer keeps `<img src="{{ file.x }}" alt="…"
   width="…">` and removes images with literal, third-party, `data:` or
   malformed sources and disallowed attributes, reporting the removal. The
   editor refuses an `<img>` naming a document and one without `alt`.
   Rendered mail with a hosted image passes the Family and readiness delivery
   checks only when its origin is the deployment's. The email layout adds the
   image style after the checks.
8. References: the uses function finds a slug in active campaign content
   (including the Testing draft and unselected email templates), in a pending
   configuration request, and in unsent outbox mail including paused
   messages. It ignores applied/failed/cancelled requests, delivered mail,
   and archived campaigns that are no longer current.
9. Deletion and renaming are refused while in use, by both the view and the
   database triggers, with the uses listed. A deletion naming any file in use
   deletes nothing; one that fails part-way says so. A deletion racing a
   content save
   serializes, so the content save or the deletion fails and never both
   succeed. The token is unchanged after a rename.
10. Storage: files are written `0600` under `hosted-files/` with no
    user-controlled path. Orphans are swept under the lock. A leftover file
    without a row is never served. Backup archives include hosted files.
11. Permissions and audit: Staff and Ministry leaders are denied every Admin
    route. Uploads, slug changes and deletions write their audit events with
    only closed fields.
12. Ingress rendering: the upload route admits 11 MB, every other route 6 MB,
    and `/files/` responses are buffered.

A browser test uploads a PDF and an image, copies both placeholders into a
page's content, sees the image and downloads the PDF from the Family page,
tries and fails to delete the in-use file, removes the references, and deletes
both files. This browser test is deferred, since the browser suite serves
pre-rendered pages without a live server
([#346 comment](https://github.com/epiphany40223/parishkit/issues/346#issuecomment-5901731922)); the same flow runs
through the real views and PostgreSQL in
`test_placeholders_render_on_pages_and_guard_rename_and_delete`.

## Admin decisions
