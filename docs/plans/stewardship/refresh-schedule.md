# ParishSoft refresh schedule and data age

Design plan for
[#632](https://github.com/epiphany40223/parishkit/issues/632) (one
integrated refresh schedule) and
[#510](https://github.com/epiphany40223/parishkit/issues/510) (what "fresh
ParishSoft data" means), which also absorbs
[#630](https://github.com/epiphany40223/parishkit/issues/630) (hourly quick
updates). The normative behavior lives in the specifications; this plan
records the research behind it, a worked Production example, the open
decisions and the delivery order. It does not repeat the requirements:

- the schedule model, slot identities, daylight saving and stored settings:
  [refresh schedule](../../specs/stewardship/background-processing/spec.md#refresh-schedule);
- the settings page, its preview and cost estimate:
  [ParishSoft refresh schedule settings](../../specs/stewardship/admin-portal/spec.md#parishsoft-refresh-schedule-settings);
- data age, the connection signal and the alarm:
  [ParishSoft data age and connection](../../specs/stewardship/operations/spec.md#parishsoft-data-age-and-connection).

## Why the design changes

- **Quick updates bring in nothing.** ParishSoft's change list has returned
  an empty list for every query in Production (494 of 494 when #510 was
  filed). Production has therefore had new ParishSoft data only from full
  refreshes.
- **They still cost a lot.** On 2026-10-05 the quick updates every 15
  minutes took a median of 134 s each, about 15% of the day, while a full
  refresh took 437 s.
- **"Fresh" meant "ParishSoft answered".** The staleness alarm and the
  bulk-send hold measured the age of the newest promoted snapshot, and an
  empty quick update promotes one. The alarm stayed quiet while Family
  changes were hours old.
- **The form refused the sensible choices.** The integration form refuses
  any schedule whose longest gap exceeds `source_stale_seconds` (30
  minutes). With at most eight full refreshes a day, "Off" and "Hourly"
  quick updates were always refused, so the Administrator could not turn
  off the work that brought in nothing.
- **Times were hard to enter and had a fixed cap.** Full refresh times are a
  comma-separated text box capped at eight, and nothing showed how a
  schedule meets the reminders' lead and send windows
  ([#587](https://github.com/epiphany40223/parishkit/pull/587)).

## Research notes

Industry practice for recurring schedules with exceptions, surveyed on
2026-10-06 for #632. Every product that handles recurrence well uses the same
four parts:

1. a rule that generates run times;
2. exceptions that remove times from the rule;
3. a live list of upcoming runs in plain language;
4. a stated rule for daylight-saving changes.

Items not confirmed from a fetched source are marked *unverified*.

### Calendars

- **iCalendar (RFC 5545).** The run set is the times generated by RRULE
  (§3.8.5.3, value type §3.3.10) and RDATE (§3.8.5.2) minus the times in
  EXDATE (§3.8.5.1): "gathering all of the start DATE-TIME values generated
  by any of the specified RRULE and RDATE properties, and then excluding any
  start DATE-TIME values specified by EXDATE". "Every 20 minutes from 9:00
  AM to 4:40 PM every day" is one of the standard's own examples
  (`FREQ=DAILY;BYHOUR=9,…,16;BYMINUTE=0,20,40`). For daylight saving,
  §3.3.10 says a generated instance at a nonexistent local time "MUST be
  ignored and MUST NOT be counted", while the same section also refers such
  times to §3.3.5's rule for an explicit DATE-TIME (a repeated time is its
  first occurrence; a nonexistent one takes the offset from before the gap,
  which moves it forward). Libraries differ, so a product must pick one rule
  and state it. ParishKit's existing resolver moves a nonexistent time to
  the first real instant after the gap, the §3.3.5 reading, so unlike the
  "ignored" reading no refresh silently disappears on the spring change.
  Sources: [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545),
  [3.3.10](https://icalendar.org/iCalendar-RFC-5545/3-3-10-recurrence-rule.html),
  [3.8.5.3](https://icalendar.org/iCalendar-RFC-5545/3-8-5-3-recurrence-rule.html).
- **Google Calendar.** A "Does not repeat" menu of common patterns plus
  "Custom…" (every N days or weeks, weekday toggles, an end condition).
  Exceptions are edits to one occurrence ("This event / This and following
  events / All events"). The calendar grid is the only preview. A cap of
  730 occurrences per series is reported but *unverified*.
  [Help 37115](https://support.google.com/calendar/answer/37115),
  [How-To Geek](https://www.howtogeek.com/719013/how-to-add-edit-or-delete-recurring-events-in-google-calendar/).
- **Outlook.** A recurrence pattern (how often) and a range (how long);
  single occurrences can be changed or deleted, which works like EXDATE. A
  one-line summary sentence of the pattern is *unverified*.
  [RecurrencePattern](https://learn.microsoft.com/en-gb/office/vba/api/outlook.recurrencepattern.recurrencetype),
  [Graph recurring events](https://learn.microsoft.com/nb-no/graph/outlook-schedule-recurring-events).
- **Apple Calendar.** A Repeat menu of presets plus Custom, with "every N",
  weekday boxes and patterns such as "On the third Thursday".
  [Apple Support](https://support.apple.com/guide/calendar/set-up-a-repeating-event-icl1018/mac).

### Backup and job schedulers

- **Synology Task Scheduler.** Days to run on, then "First run time",
  "Frequency" (every N minutes or hours) and "Last run time". Forum posts
  show users who expected round-the-clock runs and got one hour of them
  because the last run time defaulted, which argues for showing the resulting
  run list. Active Backup's allowed and disallowed backup window grid is
  *unverified*.
  [Task Scheduler](https://kb.synology.com/en-global/DSM/help/DSM/AdminCenter/system_taskscheduler?version=6),
  [SynoForum](https://www.synoforum.com/threads/scheduled-task-every-minute-only-runs-for-one-hour.14043/),
  [Hyper Backup](https://kb.synology.com/en-global/DSM/help/HyperBackup/data_backup_settings?version=7).
- **Veeam.** Modes "Daily at this time", "Periodically every N hours or
  minutes" (counted from midnight), "Continuously" and "After this job". A
  Time Periods grid of weekdays by hours marks each block **Permitted** or
  **Denied**; a job can be stopped when it leaves the window, and a denied
  run starts as soon as the denied period ends.
  [Enterprise Manager](https://helpcenter.veeam.com/docs/vbr/em/cd_jobs_schedule.html?ver=13),
  [Agent for Windows](https://helpcenter.veeam.com/docs/agentforwindows/userguide/backup_job_schedule_server.html).
- **Time Machine.** No time picker at all: Hourly, Daily or Weekly. The
  extreme of presets only.
  [Apple 104984](https://support.apple.com/en-my/104984).
- **AWS EventBridge Scheduler.** `rate()`, `cron()` and one-time `at()`
  schedules in any IANA time zone. The console is reported to show the
  **next 10 trigger dates**, live as you edit, in UTC or local time
  (*unverified*: console only, with no API for it). On daylight-saving days a
  cron time in the missing hour is skipped and one in the repeated hour runs
  once; `rate(1 days)` is a fixed 24 hours and drifts against the clock.
  [Schedule types](https://docs.aws.amazon.com/scheduler/latest/UserGuide/schedule-types.html),
  [debugging EventBridge cron](https://alexwlchan.net/2021/debugging-eventbridge-cron/).
- **GitHub Actions.** Plain cron, UTC by default, at most every five
  minutes; runs can be delayed under load and some queued jobs dropped. No
  preview.
  [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- **Jenkins.** Cron text plus `H`, a stable per-job hash that spreads start
  times. Under the field it prints "Would last have run at … would next run
  at …" with the time zone, and suggests spreading load. A community thread
  found a server and user time-zone mismatch only because the preview
  printed the zone.
  [Community thread](https://community.jenkins.io/t/build-periodically-schedule/6534),
  [Jenkins cron summary](https://tool.crontap.com/jenkins-cron).
- **Kubernetes CronJob.** An IANA `timeZone`; `concurrencyPolicy` decides
  what happens when the previous run is still going (Allow, Forbid to skip
  the new one, Replace); `startingDeadlineSeconds` skips a run that is too
  late. No preview.
  [CronJob](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/).
- **Cron builders.** crontab.guru and cronstrue pair the expression with a
  live English translation; crontab.guru's next-runs list is *unverified*.
  Their authors argue the translation, not the builder, is the real help.
  [crontab.guru](https://crontab.guru/),
  [cron expression descriptor](https://bradymholt.github.io/cron-expression-descriptor/),
  [GUI cron builder](https://dev.to/sendotltd/a-gui-cron-builder-and-why-building-is-way-easier-than-parsing-2bkn).

### Maintenance windows

- **Datadog downtimes.** One-time or recurring, with a start, time zone,
  repeat frequency, weekdays, **duration** and an end; advanced patterns take
  an RRULE. Business hours are expressed as two recurrences. "Preview
  affected monitors" previews scope, not dates.
  [Downtimes](https://docs.datadoghq.com/monitors/downtimes/),
  [examples](https://docs.datadoghq.com/monitors/downtimes/examples/).
- **PagerDuty.** Presets "start now and end in 15 or 30 minutes, 1, 2 or 4
  hours", or a scheduled start in a time zone; recurring windows need the
  API. One list shows windows happening now, future and past.
  [Maintenance windows](https://support.pagerduty.com/main/docs/maintenance-windows).
- **Grafana mute timings.** Each interval has a time range (start inclusive,
  end exclusive), weekdays, days of the month, months and a location;
  fields in one interval must all match and several intervals add up.
  Silences are one-off windows.
  [Mute timings](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/mute-timings/),
  [mute timings or silences](https://grafana.com/blog/mute-timing-vs-silences-in-grafana-alerting-how-to-pick-the-best-fit-for-your-use-case/).

### Thermostats and smart-home schedules

- **Nest.** A timeline per day: tap to add a setpoint and drag it. Presets
  (Comfort, Eco, Sleep), copy a day or a week. A hard spacing rule:
  "Adjacent temperatures … must be at least 60 minutes apart."
  [Google Home help](https://support.google.com/googlehome/answer/10185085?hl=en).
- **ecobee.** A calendar view of named activities that can expand to
  30-minute cells; "Copy Schedule" to other days.
  [ecobee](https://www.ecobee.com/en-us/citizen/a-smarter-simpler-way-to-manage-comfort-at-home/).
- **Honeywell Home.** Four named periods a day and day groupings (every day
  the same, weekdays and weekends, each day different).
  [T10 scheduling](https://docs.honeywellhome.com/t10-t10plus-pro-product-data/Scheduling.htm).

### General guidance

Nielsen Norman Group's date-input guidance: accept flexible typed input,
rule out illogical choices such as an end before its start, explain errors
rather than only rejecting, and offer a short list when choices are few
([date input](https://www.nngroup.com/articles/date-input/)). #631 applies the
first point to time entry.

### What the design takes from this

1. **Rules plus additions, minus exceptions** (RFC 5545), shown as visible
   layers in plain words, never cron text.
2. **Range rules with an explicit last run** ("every 30 minutes from 06:00
   to 22:00"), like Synology, with the anchor stated (the "from" time).
3. **Presets first** (Time Machine, PagerDuty, Google), opening the editor
   prefilled.
4. **Blocked windows shaded on a week grid** (Veeam), labeled with their
   cause, so automatic blocks read differently from the Administrator's own.
5. **Removed times stay visible**, struck through with the reason, rather
   than vanishing as a deleted occurrence does.
6. **A live preview of upcoming runs with the time zone named** (Jenkins,
   and reportedly EventBridge). Refresh times are the parish's wall-clock
   times (decision 18), so the preview names the parish zone and, when the
   browser's differs, shows the browser's equivalent too.
7. **Every dropped run explained in the preview**, not only at save.
8. **A stated spacing rule** (Nest's 60 minutes; ours is 15) with a
   documented precedence: Full beats Quick.
9. **Per-day variation by copying** (Nest, ecobee, Honeywell), deferred
   until someone needs it.
10. **One stated daylight-saving rule, visible on the days it applies.**
    ParishKit keeps its existing resolver (the earlier of a repeated time;
    the first real instant after a gap), RFC 5545's §3.3.5 reading rather
    than §3.3.10's "ignored", so existing slot identities do not change and
    no refresh silently disappears.
11. **The cost next to the schedule.** None of the surveyed products shows
    one; it is ParishKit's own addition, because ParishSoft time is the
    real limit that the old cap of eight stood in for.
12. **Overlaps and late runs decided and stated** (Kubernetes): refreshes
    already never overlap, and after downtime only the latest slot runs.

## Worked Production example

Production on 2026-10-05: full refreshes at 00:00, 08:00, 10:00, 12:00,
14:00, 16:00, 18:00 and 20:00, quick updates every 15 minutes, and Family
reminders on Tuesday and Thursday at 06:00 (lead window 04:00–06:00, sending
until about 07:00). The estimate uses the medians above (full 437 s, quick
134 s).

| Schedule | Full | Quick | ParishSoft time a day | Share of the day |
| --- | --- | --- | --- | --- |
| Today (quick every 15 min; a quick due with a full joins it) | 8 | 88 | about 4 h 15 min | 17.7% |
| Quick hourly, skipping hours with a full (#630) | 8 | 16 | about 1 h 34 min | 6.5% |
| The same on Tuesday and Thursday (04:00–07:00 excluded) | 8 | 13 | about 1 h 27 min | 6.1% |
| Quick off | 8 | 0 | about 58 min | 4.0% |

With the new [data age](../../specs/stewardship/operations/spec.md#parishsoft-data-age-and-connection),
the longest wait for new data in every row is the 8 hours from 00:00 to
08:00. The alarm sounds when a scheduled full refresh is more than 30 minutes
late, not when 30 minutes pass without any refresh. Every time here is on
the hour, so coverage leaves out only the quick update at each full time;
on Tuesday and Thursday the 04:00, 05:00 and 06:00 quick updates fall in the
window, which ends at 07:00, so 07:00 runs. The quick setting no
longer changes how fresh the data is counted as, so "Off" and "Hourly" become
valid. With a nightly refresh only, the data-age alarm sounds if the 02:00
refresh has not run by 02:30.

## Open decisions

Each has a recommended default, and the specifications are written to the
default. They are posted, with the same numbers, on
[#632](https://github.com/epiphany40223/parishkit/issues/632#issuecomment-6022799750)
(decision 18 and the revisions after review in
[a later comment](https://github.com/epiphany40223/parishkit/issues/632#issuecomment-6023016671),
the second and third correction rounds in
[another](https://github.com/epiphany40223/parishkit/issues/632#issuecomment-6023180420)
and [a third](https://github.com/epiphany40223/parishkit/issues/632#issuecomment-6023305360));
the implementation follows the default unless the Administrator decides
otherwise. Items 1–5 are about data age (#510), 6–14 about the schedule
(#632, #630), 15–17 about storage and upgrade, 18 about time zones, and
19–23 about the settings page and command line (posted with the remaining
slices).

1. **What counts toward data age.** Default, split in two: the alarm and the
   bulk-send hold measure from the newest promoted **full** refresh only,
   since only a full refresh re-reads everything; the displayed "data as of"
   also moves with a quick update that brought in at least one change.
   An empty quick update proves only the connection.
2. **When data counts as out of date.** Default: when a scheduled full
   refresh that should have replaced the data is more than the lateness
   margin overdue, counting only due times after the current schedule first
   became effective (not every configuration activation) and not recorded
   as skipped. A slot already overdue when a schedule changes stays overdue
   until a full refresh promotes, so saving cannot silence the alarm. The
   catch-up after a hold keeps the hold's allowance until it promotes or
   fails. Alternative: a fixed allowed age
   of the schedule's longest gap plus a margin, which alarms hours later
   after a missed daytime refresh.
3. **The lateness margin.** Default: reuse `source_stale_seconds` (30
   minutes) as the margin, so no new setting is needed; the release notes
   say that its meaning changes.
4. **The connection signal.** Default: one line, "Failing since", else "Not
   checked since", else "Working", shown apart from "data as of", with no
   new alarm; superseded or cancelled quick updates and held or skipped
   slots are not attempts.
5. **Go-live readiness.** Default: unchanged; it still requires a full
   refresh within `source_stale_seconds` before going live.
6. **Default schedule on the settings page.** Default: the nightly full
   refresh at 02:00 plus hourly quick updates (#630). A stored document
   that names no schedule keeps today's defaults until it is saved.
7. **Quick updates near a full refresh.** Default: a rule's quick update is
   left out when a full refresh falls at or after it and less than one rule
   step after it, or less than 15 minutes before it, on the same day with no
   wrap past midnight (#630's "skip an hour that already has a full
   refresh").
8. **Refreshes inside an excluded window.** Default: skipped, not moved to
   the window's end, and nothing replaces them: when the latest due slot is
   skipped no slot is created, rather than falling back to an older one.
   The decision (skipped or held) is recorded when the slot falls due, for
   every undecided due slot (including after scheduler downtime), so a later
   change to the windows cannot turn a skip into a missed refresh, nor a
   held slot into a skip. Windows are applied before the bulk-send hold:
   skipped means not due, held means due.
   Alternatives: run once when the window ends, as Veeam does; or freeze
   each email's window when its lead window starts, instead of recording
   each skipped slot.
9. **How long the send window is.** Default: open while the email's send
   still has active work (counted for that occurrence alone), but never past
   its due time plus the two-hour send allowance, so a stuck send cannot keep
   refreshes skipped; before and after that, an estimate from the
   campaign's most recent completed Production send of the same kind (else
   the other kind), from its due time to its last message's final state,
   rounded up to 15 minutes, at least one hour and at most the two-hour send
   allowance; one hour before any send has run. Nothing is skipped while
   Production delivery is paused.
10. **The nightly refresh and excluded windows.** Default: the nightly is
    never excluded (it already runs during a send); the page and the existing
    WARNING flag it when it falls inside a window.
11. **Different schedules on different weekdays.** Default: not now. The
    reminder windows are excluded automatically from the actual reminder
    times, which covers the Tuesday and Thursday case; a weekday filter on a
    rule can be added later as an optional setting.
12. **The quarter-hour grid.** Default: new times are on the quarter hour,
    and existing off-quarter-hour full times are kept while the
    Administrator keeps them; the grid is read-only and editing is through
    presets and rule rows. Click-to-edit grid cells are deferred because of
    their keyboard and screen-reader cost.
13. **The cost warning threshold.** Default: warn above 25% of the day;
    never refuse.
14. **Maintenance windows.** Default: no automatic source exists today, so
    the Administrator's "skip from–to" exceptions cover them; automatic
    exclusion of upgrade windows is deferred.
15. **Where the new settings are stored.** Default: optional keys added to
    `source-cadence-v8`, as #465 did, so every earlier document stays valid;
    the schema checks only their shape and spacing, and the form and command
    line check that the lists match the rules. Removing the cap of eight
    means a release from before this change refuses a document with nine or
    more times, so after such a save an older image needs a backup restore.
    Alternative: a new validation schema name, which the configuration
    table's check constraint and every SQL guard that lists the accepted
    schema names would have to learn.
16. **The tick guard.** Default: a forward migration so the database admits a
    quick tick only at a listed quick time. Alternative: no guard change. The
    current guard admits a quick tick only on a UTC quarter hour (or hour),
    and refuses, say, 08:10; since new quick times are on the local quarter
    hour, which is a UTC quarter hour in every zone whose offset is a whole
    number of quarter hours, storing `delta_refresh: quarter_hour` beside the
    list would let the guard admit every listed quick time as part of a
    looser superset.
17. **Existing stored schedules.** Default: no stored document is rewritten,
    and their slots are created exactly as today until the Administrator
    changes the schedule; the new keys are written only then, not on saving
    other settings. An existing schedule has no "skip refreshes around Family
    emails" setting and never skips until an Administrator saves one with
    it. Data age and the bulk-send hold change for every schedule in
    delivery step 1.
18. **Time zone of schedule times.** Default: refresh times stay entered and
    shown in the parish's time zone, as they are today, as a recorded
    exception to the browser-local rule
    ([#558](https://github.com/epiphany40223/parishkit/issues/558)). A
    refresh schedule is a recurring wall-clock schedule, not a set of
    instants: the parish's daylight-saving changes decide when each refresh
    runs and when the reminders it avoids are due, and a time entered in
    another zone would move against the parish's clock twice a year when the
    two zones change on different dates. #558 already names reminder send
    times as the kind of campaign-calendar time that may be an exception.
    The zone is the one the scheduler resolves refresh times in: the
    current campaign's, else the parish's. The page names it ("the refresh
    schedule's time zone") beside the editor and, when the browser's
    zone differs, shows each preview time in the browser's zone as well.
    Alternative: enter times in the browser's zone and convert them with
    today's offset, which is simple for the common case of a browser in the
    parish's zone but wrong part of the year for anyone else.
19. **The switch on a converted schedule.** Default: **skip refreshes
    around Family emails** starts off for an existing schedule shown as
    rules, because it never skips today, and the review names turning it on
    as a difference; it starts on only when no schedule is stored, and
    presets leave it alone. Alternative: on for every schedule the page
    shows, so the first saved edit of any kind also starts skipping.
20. **How existing full times are shown.** Default: one "Full at" row per
    stored time, with no rule inferred, so the page shows exactly what is
    stored; the Administrator can then pick a preset. Alternative: infer
    rules ("Full every 2 hours from 08:00 to 20:00"), which reads better but
    can surprise when the inference is not what was meant.
21. **Where the rules are checked live.** Default: only on the server, by a
    read-only check request each time typing pauses, since the preview
    needs the server anyway. Alternative: a copy in the page script pinned
    by a shared case table, as the mail repeat panel does.
22. **What the review shows.** Default: the full and quick times added and
    removed and the switch, in words, plus the converted-schedule
    differences, instead of the stored settings' diff.
23. **The grid's timing.** Default: the per-day list ships with the editor
    and the grid follows in its own PR, so the editor can be checked and
    used sooner.

## Delivery plan

Smaller coherent PRs under the
[automated delivery cycle](overall.md#automated-phase-delivery-cycle), each
with an independent review, and local human verification for those that
change Admin pages. `main` is production, so no PR lets a document store
settings that the deployed scheduler cannot run. Production configuration
changes and deploys stay the Administrator's decision.

**Status (2026-10-09).** Steps 1–3 are merged: data age and connection in
[#654](https://github.com/epiphany40223/parishkit/pull/654), 2a in
[#677](https://github.com/epiphany40223/parishkit/pull/677) (migration 0011)
and 2b in [#687](https://github.com/epiphany40223/parishkit/pull/687)
(migration 0014). Flexible time entry (#631) landed in
[#646](https://github.com/epiphany40223/parishkit/pull/646). No page or
command writes `refresh_rules` yet, so every stored schedule, Production's
included, still runs as an existing schedule. Steps 4 and 5 are re-sliced
below, after a short spec update, into
[remaining slices](#remaining-slices).

1. **Data age and connection (#510).** No schema change. On its own this
   lets the Administrator choose hourly or no quick updates on today's page.
   - Compute the last full refresh, "data as of" and the next due full
     refresh from the stored schedule as it is today, counting due times
     only after the current schedule first became effective; "data as of"
     reads a quick update's change count from the snapshot cursor's
     `changes`.
   - Drive the `source_stale` alarm from the out-of-date rule.
   - The bulk-send hold: `deltas_skipped` counts held daytime full slots as
     well as quick ones and looks for requests from the overdue full slot's
     due time, not the newest full refresh's read, so the allowance works

  another writer of the same validated settings. Slice 3's save is the
  first time a stored schedule can change shape; the switch starts off for
  a converted schedule and the review names every difference, so nothing

  on a night without a reminder the next morning, as for 2a and 2b.

  paragraph, so the two merge in either order.
- The preview's window estimate must match the scheduler's; slice 2's
  parity tests pin it to `send_windows`.

## Rejected approaches

- **A higher fixed cap.** The 15-minute spacing and a visible cost estimate
  express the real limit.
- **Keeping a fixed 30-minute freshness window.** It made data look fresh
  when it was hours old, and refused the schedules that save the most work.
- **Cron text for Administrators.** Every surveyed product aimed at
  non-specialists avoids it; a cron field suits operators, not a mid-level
  IT admin.
- **A click-to-edit grid as the only editor.** Hard to use by keyboard or
  screen reader, and hard to read as a rule; it stays a preview.
- **Dropping quick updates entirely.** They double as a connection check and
  would bring in data if ParishSoft fixes its change list (#510).
- **Rewriting stored settings in a data migration.** Applied configuration
  versions are immutable history; reading the old keys as today is safer.
