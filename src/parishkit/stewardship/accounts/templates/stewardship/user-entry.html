{% extends 'stewardship/admin-base.html' %}{% load static i18n stewardship %} {% block title %}{% if new %}{% translate "New user" %}{% else %}{% translate "Edit user" %}{% endif %}{% endblock %} {% block head %}{% if new %}{% endif %}{% endblock %} {% block content %}{% comment %} New user and Edit user (#952; user_views._entry). One page with three fields: Email (typed on New, shown on Edit, where it never changes), Name and Role. Review (Add the user on New, Save on Edit) posts here without a page load (data-review-open, UX conventions "Review dialog", #750): while the answer is prepared the form is inert and busy; an accepted review opens the shared review dialog below with user-review.html, whose Apply posts to Users and follows the change, then returns to Users, whose status line says what was applied. On New the dialog is a confirmation (UX conventions, "A confirmation when Review would only repeat the page", #1356): every value is on the form behind it, so it says in one sentence what Apply does (user-review-summary, its description) and adds only the Administrator warning. On Edit it is a compact review ("A compact review when Review adds only the old value"): one line per changed field, "Role: old → new" (user-review-summary again), and the Administrator grant or removal warning. A review refused for a field's value keeps the dialog shut: ui-v1.js marks each field and shows the summary from this page drawn again with the errors. Any other refusal (a stale page, a refused Apply) shows inside the dialog. Each field's error line is reserved (.field-error-line), so a message coming and going never moves the controls below it (no layout shift). On New, users-v2.js asks the server (user_name_suggestions, a CSRF POST) when the Administrator leaves Email: it shows the address's problem at the field, or fills in the first ParishSoft name (never over a typed Name), offers the others in the datalist and says which it found in the Name's help line, which is always there. That line is one line high whatever it says: a long answer is cut short with an ellipsis and shown whole in its title (and read whole through the Name's aria-describedby), so the Role choices below never move under the pointer (#736). On Edit, Save is available only once the Name or role differs from the saved user (data-require-change, #921), with the reason after it. On both, Add the user or Save waits for an Email (New) and a Name, and while the Email check has marked the address (data-require-complete, #1330), with the reason in the line reserved under the buttons. On Edit, the lower roles are unavailable for the reader's own user (an Administrator never demotes themselves, Administrator decision 2026-10-11) and for the only Administrator, with the reason in the line under the roles, which is always there (#563); the server refuses that change anyway. The recorded Google identities of the address each get a Sign-in activity button (#953), posting the identity, never in an address. {% endcomment %}
