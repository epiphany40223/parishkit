The first box, Start the load, is In progress from the moment the load is requested until a worker picks the run up (#1916; campaign_wizard.load_stages); while it is, the reserved line says the run waits for the background service (stages.QUEUED). That line sits in one grid cell over an invisible copy of the sentence, so it keeps the sentence's height in every state and nothing moves when the first real stage starts. ``load`` is offer (not loaded yet), loading, failed, empty (a full load succeeded but no Families matched, #1587) or loaded. Refresh from ParishSoft draws it in wizard mode (source-refresh.html) from the stepper's facts, with ``families`` and ``as_of`` once loaded; while the load runs, live-status-v1.js polls the run's passive status fragment (?view=load, ``campaign_wizard.load_status``), which draws this same region from the run alone and never renews idle time. The region is not aria-live, since its counts change on every poll: its data-live-announce sentence is read out by the page's announcer (outside the in-place region) only when it changes. Once the run has ended, its hidden follow-up link re-reads the page in place, so the stepper's marks, the action row's Continue and this region's full state (the Family count, or Try again) come in with no reload. Every state draws the same lines and boxes, and the summary line sits in one grid cell over invisible, aria-hidden copies of every state's wording (with all its links), so it is as tall as the longest wording at every width, zoom and font (ui-v1.css): the switch from one state to the next moves nothing (no layout shift). When the pressed button's in-place answer leaves no button, the summary line takes focus (data-in-place-focus): it names the new state and is already in view, whereas the region itself, the fallback, could scroll the page to show its bottom edge. {% endcomment %}
