{% comment %} A binary choice (#1535; ui-conventions spec, "Binary choices"): a short visible label and two equal segments, each a link to this page with that choice, the chosen one marked aria-current="page" and filled. ui-v1.js follows each link in place (a[data-in-place]), so choosing a segment needs no Apply button, keeps the reader's place and focus on the segment, and replaces the address. The pair is drawn inside a region or a data-table-sync node of the page, so every in-place answer redraws its links with the page's current view state. {% include "stewardship/components/segmented-choice.html" with choice_id="dashboard-mode" region_id="response-dashboard" label=_("Responses shown") first_key="mode-production" first_label=_("Production") first_href=production_url second_key="mode-testing" second_label=_("Testing rehearsal") second_href=testing_url chosen=testing|yesno:"mode-testing,mode-production" %} - choice_id: the pair's id, and the prefix of its label's id. - label: the visible label that names the group. - tip (optional): help for the label, in a toggletip beside it. - region_id: the region of the including page that each link names as its fragment (required: the ordinary load lands there). - first_* / second_*: each segment's data-in-place key (stable, so the segment is found again for focus and its text announced after the swap), its text and its href (the address without a fragment). - chosen: the key of the segment the page shows. - spinner (optional): the choice's re-read can take seconds (a report's Families counted, #2324), so the pair is marked data-busy-control and draws the shared working spinner (components/spinner.html) after its segments, hidden in space it always keeps; while the in-place read the reader started from this pair is under way, ui-v1.js marks the pair data-busy-working and ui-v1.css shows the spinner (ui-conventions "Working spinner"), so nothing moves. - filters (optional): the pair sits beside the page's filter form, so each segment is marked data-in-place-filters and the form is set to the filters the new view applied. A page whose filters are private POST state (the family directory) cannot put them in a link, so it passes action instead of the hrefs: each segment is then a small POST form to that action (a read, data-in-place-read), carrying fields (a dict, such as the page's query_fields) as hidden fields, except the one named name, which its button sends with first_value or second_value. The button looks and acts as the link would; the form's data-in-place key finds it again. Both segments are always bold and fixed in size (ui-v1.css), so choosing one changes only colours (no layout shift). {% endcomment %}
