{% load i18n stewardship %}{% comment %} The shared confirmation dialog of action tables (admin-portal spec, "Row actions and confirmation", #879): a native modal that ui-v1.js opens from a control marked data-confirm-open="" (a row's Delete, or the bulk bar's button for the ticked rows). It never uses confirm(). - title_one / title_many and done_one / done_many are the title and the announcement after success, with {name} (the row's data-confirm-name) or {count} filled in by the script. - body and caution say what the action does and what it cannot undo. - form_id names the table's form: confirming posts its fields (CSRF and any base version) plus the chosen rows, without a page load. - The status line ("Working…") is reserved under the buttons, and a refusal is shown below that, so neither ever moves a button. The dialog is anchored to the top of the window (ui-v1.css), so a growing dialog grows downwards. - fallback names the element that takes focus when the control that opened the dialog is gone (its row was removed). - cancel (optional) replaces the Cancel label, and plain_accept draws the accept button as a primary button rather than a destructive one: the Basic / Advanced toggle's "Keep Advanced" and "Switch to Basic" (components/editor-mode.html, #1121), which removes nothing. For a bulk action that records something rather than removing it (the Ministry follow-up queue's bulk outcomes, #1131): - The opening button may carry its own data-title-one, data-title-many, data-done-one, data-done-many and data-confirm-body, which replace the dialog's, so several bulk buttons share one dialog. - A button marked data-confirm-kind is available only while every ticked row is of that kind (rows marked data-confirm-kind too; ui-v1.js wireSelection, which says why in the bulk bar's reason line), so the dialog always acts on every ticked row. - Its name and value are posted with the rows (the outcome). - fields_template is a template of fields shown in the dialog; the dialog then sits inside the table's form (form_id), marked data-require-complete, so the fields are posted and Confirm (a submit button, accept_type="submit", whose click never submits natively) waits for them, with the hint line accept_hint names. Fields marked data-confirm-reset go back to their defaults each time it opens. - plain_accept=True draws Confirm as an ordinary primary button, not a destructive one (the same option as #1145's). With review=True it is instead the shared review dialog of Admin editors (UX conventions, "Review dialog", #750): a form marked data-review-open="" posts its Review without a page load, and the server's review (a fragment marked data-review-answer, holding the signed preview) is shown in the dialog's body, which scrolls while the title and buttons stay in view. The body is a focusable region named by the title, so a keyboard can scroll a long review that holds nothing else to focus (a repeat's thirty reminders). - title names the change and labels the dialog; it takes focus on open, never Apply, so the reader hears what is reviewed first. - apply_url is where Apply posts (action=confirm), with every hidden field of the review's fragment: its signed preview (marked data-review-preview, without which there is no Apply) and any other field an editor needs, such as a version. The answer is the change's status, which the dialog follows. - return_url, when set, is the table page a New or Edit page returns to once the change is applied; without it the page's regions are redrawn in place. Either way outcome_id names that page's reserved status line (components/review-outcome.html), which then says what was applied and when. - fallback is as above. - describedby, for a confirmation (UX conventions, "A confirmation when Review would only repeat the page"), is the id of the review fragment's one-sentence summary, which then describes the dialog. - redraw_answer=True redraws the page's regions from the address Apply's answer ended on (the page naming its change, ?request=), not from the page's own address, and makes it the page's address: Create the campaign's own address can only be refused once the campaign exists. {% endcomment %}{% if review %}
