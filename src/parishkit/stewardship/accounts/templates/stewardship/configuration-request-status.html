{% load i18n stewardship %}{% comment %} A configuration change's live status: Change status draws it, and so does an in-place settings page's review region (#532), which passes status_url (Change status's passive read, naming that page with in_place) so the poll never extends the sign-in. Read that way, the status carries follow_url once the change is applied: a hidden follow-up that refreshes the settings page in place, quietly, so its form starts from the applied settings. A change that was not applied leaves the page alone, so its form keeps the version it was reviewed at. A refused live end-date change (#944) says why, in the same paragraph a failure's explanation always takes, so the settled status occupies the same place as any other. The pages a message names are linked with menu_link, greyed out as the menu greys them (#521). This needs no flag for where the status is drawn: Campaign settings' review dialog reads the status as plain text (ui-v1.js changeStatus), so the link never shows on the page it names. The template[data-live-refused] is what live-status-v1.js shows, in place of the running status, when a status read is refused (signed out, or the reader lost access, such as by a change that removed their own access): a plain final status, never an indefinite wait (#952). The change that created the deployment's first campaign (#142) is given refresh_key once applied: inside the live region, so it appears in place when the status turns Applied, it offers the campaign's first full ParishSoft refresh, posted to Refresh from ParishSoft's own action. {% endcomment %}
